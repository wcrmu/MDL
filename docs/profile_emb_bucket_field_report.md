# Profile Emb / Bucket 逐字段替换评估报告

## 先读这个：10 个文件 vs 线上 1 小时 ~500 个文件

- 本 profile：`max_files=10`，实际扫描 **10** 个文件，`rows_scanned=18720`，`agg_rows=18720`。
- 线上 1 小时约 **500 文件** ⇒ 当前样本大约是 **1/50 小时文件量**。
- 因此：**不是所有字段的 recommended_bucket / suggested_dim 都能直接信。**

### 什么样的字段，10 个文件就够？

- **R1 低基枚举 / 封闭集合**：如 `plat_hn`(7)、`language_hn`(11)、`currency_hn`(26)、`hash_language_site_hn`(56)、`scene_id_hn`(104)。
- 特征：distinct 很小、leaf 很大、top 值反复出现（`hash_language_site_hn` top5 已覆盖约 59%）。
- 扩到 500 文件，基数多半只在同一量级晃（几十→一两百），**不会突然变成百万级**。
- 对这类字段：profile 的“该不该用大表”结论可信；但要注意 scanner 候选桶从 `2^10=1024` 起，且 `cardinality_headroom=1.5`，**推荐桶往往偏保守偏大**（所以会出现 56 个值却推荐 4096）。

### 什么样的字段，10 个文件不够？

- **R4 高基数 ID / 长尾 bag**：`goods_id`/`sku_id`/`i2i_*`/`*_spec*`/UPS 序列 goods。
- 特征：distinct 已经很大、uniq 高、top 值几乎不重复；推荐桶经常顶到很大。
- 扩到 500 文件，distinct 还会明显涨（粗估可达数倍～一个数量级，视重叠而定）。
- 对这类字段：**禁止把 10 文件推荐当最终值**——既不要按候选侧 8M 去砍共享 `goods_id` 表，也不要无脑跟到 128M/512M。

### `hash_language_site_hn` 为什么看起来“没区别”？

- 当前与 profile 都是 `4096/16`，**本来就没有替换差**。
- 旧报告因 “distinct≤64 且桶≥4096” 误打成 L1，属于逻辑 bug，已修。
- 正确读法：R1 可信；表已经不大；若想更省，可讨论压到 512/1024，但那是**比 profile 更激进**，不是“跟 profile 替换”。

> 对比基线：git HEAD `configs/rankmixer.yaml`
>
> **重要性五级** + **样本可信度四级** 交叉使用：可信度低的字段，即使 profile 数字刺眼，也不得标成 L1。
